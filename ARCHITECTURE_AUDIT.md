# Afakpress CMS Architecture Audit

## Scope

Audited the project layers present in this repository:

- Database schema and migration SQL
- Supabase access patterns
- Authentication and admin roles
- Admin dashboard CRUD flows
- Articles, categories, regions, provinces, communes, menus, media, pages, breaking news
- Public frontend routing and rendering
- TypeScript types, validation, and build configuration
- Vercel configuration

## Critical Findings

### Database and Supabase

- The reference schema did not match the application contract. It described `users`, split `menus/menu_items`, `site_settings`, and text IDs while the app uses `profiles`, flat `menus`, `settings`, and UUID relations.
- Article relation columns were inconsistent across schema, migration, types, and runtime payloads.
- Region/province/commune seed SQL inserted text IDs such as `province-...`, which is incompatible with UUID foreign keys.
- Some migrations added only columns but did not define the complete app schema.
- RLS was not defined in a coherent way for the current browser-read architecture.
- Public/admin reads currently happen through the browser Supabase anon client. That means strict private draft visibility cannot be enforced safely until reads move behind server APIs.

### Admin and CRUD

- Articles, categories, menus, media, pages, and breaking news have Supabase write flows.
- Homepage sections, comments, settings, and newsletter are partly or fully local-state only.
- Authors and region/province/commune create/edit/delete now use the Supabase-backed admin API.
- Bulk article updates mutate local state only and do not persist to Supabase.
- Category form has visible controls for order/active that were not wired into draft state.
- Media library stores URL metadata only; no real upload/storage integration exists.

### IDs and Relations

- Previous fallback data used text IDs like `province-...`, `cat-...`, `user-editor`.
- Article form values can only be safe if dropdowns use database UUIDs.
- Fallback records now use deterministic UUIDs, and payload/API validation blocks invalid UUID strings.
- Slugs are correctly used for public URLs but must never be sent to `*_id` columns.

### Authentication and Roles

- Admin auth uses Supabase Auth plus `admin_users`; this is a sound base.
- Middleware only checks for presence of the access cookie; deeper role checks happen later.
- Generic admin API now enforces per-resource role permissions server-side for all listed CMS resources.
- Super-admin-only admin user management is enforced server-side.

### Frontend and Routing

- Public routes exist for home, category, article, region, province, commune.
- Public pages depend on client-loaded CMS state, so initial static output can show fallback content until hydration.
- Header regional menu depends on `state.regions`; empty Supabase data previously made the menu disappear.
- The menu builder manages custom menus separately from the regional mega menu.

### Validation and Error Handling

- Article validation now exists client-side and server-side for UUID relations, status, slug, title, and timestamp.
- Other CRUD panels still have minimal validation.
- Server API normalization is strongest for articles; other resources remain more permissive.

## Fixes Applied

- Added UUID helpers and converted fallback IDs to UUIDs.
- Added article client validation to block slugs/names/text IDs in UUID relation fields.
- Added article API validation for UUID fields, status, timestamps, title, and unique slug.
- Aligned `cms-schema.sql` with the actual app tables.
- Added production-style UUID schema, indexes, foreign keys, status constraints, and RLS read policies.
- Reworked the Morocco region seed SQL so UUIDs are generated by the database and relations are linked through slug lookups.
- Added a bootstrap API to seed missing reference records with real UUIDs.
- Restored safe fallbacks for categories, authors, and regions so the menu and article dropdowns do not disappear when Supabase is empty.
- Added server-side resource authorization to the generic admin API.
- Persisted author CRUD through the `profiles` table.
- Persisted region, province, and commune create/edit/delete through the admin API.

## Remaining Production Gaps

- Move CMS reads behind authenticated server APIs so draft/private data is not exposed to anon Supabase reads.
- Persist comments, settings, homepage sections, and newsletter subscribers to Supabase.
- Add dedicated automated CRUD tests against a Supabase test database.
- Add real media upload/storage integration.
- Add full form validation for every CRUD panel, not only articles.

## QA Status

- Static architecture audit completed across schema SQL, Supabase access, auth, roles, admin CRUD, article relations, public routing, TypeScript validation, and deployment config.
- `npm run lint` passed.
- `npm run build` passed after running outside the restricted sandbox required by Turbopack/PostCSS process spawning.
- `npm run test:e2e` passed on Chromium: homepage, category, region, province, commune, article, admin login, and admin redirect protection.
- Full authenticated CRUD automation requires a configured Supabase test project and admin credentials. The repository currently provides only `.env.example`, so destructive create/edit/delete integration tests against Supabase cannot be executed locally without external test credentials.
